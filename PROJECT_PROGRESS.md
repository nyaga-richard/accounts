- **Master data/accounting:** Supplier, customer, cashier and chart-of-accounts APIs; account ledger, customer statement and trial balance routes. Supplier/customer/account/type screens exist; most recent type/account pages passed the 2026-10-30 build, but browser workflows have not been smoke-tested.
- **Bank statement import:** XLSX preview/import, original remarks and bank references preserved, duplicate candidates surfaced for confirmation, configurable remark extraction and audited manual review. Import UI was included in the latest passing web build; latest UI workflow has not been browser-smoke-tested.
- **Weekly closing:** Versioned snapshots, transaction-number cutoff, approval/locking, audited reopen and reclose, supplier/account snapshots and closing-detail UI. API tests cover overlap/locking/reopen/reclose behavior.
- **Weekly reconciliation:** Immutable historical snapshot tables, supplier and cheque classification snapshots, exact independent operational formulas, difference checks and approval blocked unless both differences are zero. A reconciliation UI and eligible-cheque listing endpoint were added and included in the latest passing build. UI workflow was not browser-smoke-tested.
- **Bank reconciliation:** Migrations 011–012 add posting-level allocations, one reconciliation per statement, and database guards for matched entries/approved snapshots. A typed API supports prepare/resume, suggestion-only candidates, exact manual one-to-many allocations, and approval only after every row is matched and statement/ledger closing balances agree exactly. The UI shows original remarks/references, candidate signals without auto-selection, ledger allocations and closing difference. PostgreSQL tests cover incoming/outgoing sides, duplicate bank references, exact allocation and immutable approval. `docs/BANK_RECONCILIATION.md` documents the current workflow. Unmatched bank fees/exceptions must first be entered as transactions; no separate bank-item classification workflow exists yet.
- **Opening balances:** Migrations 006–008 and 010 add pending/approved/rejected batches, line rows across accounts/suppliers/customers/cashiers, batch audit, strict NUMERIC(19,4) validation, exact account debit-credit balancing, one-approved-opening-per-entity constraints, database immutability and cutover guards, role permissions, typed API router/service, UI and `docs/OPENING_BALANCES.md`. Posting/reversal date checks prevent backdating before an approved cutover; weekly close includes an opening balance effective on the week-start date. PostgreSQL integration tests exercise balance rejection, atomic approval, rejection, and immutable history. Important limitation: subledger balances are entered independently; automated control-account mapping/reconciliation is deliberately not assumed and operators must verify subledger control totals before approval.

Search/filter/detail query is covered by PostgreSQL integration assertions, and page/API reachability/authentication returned expected HTTP statuses. Status mutation/lifecycle remains unimplemented to avoid guessing allowed cheque state transitions.

## Current accounting invariants
- Current Balance = Bank Balance + CHQ B − CHQ A.
- Net Balance = Bank Balance + CHQ B − CHQ C − Supplier Bal.
- These operational calculations are separate from formal debit/credit journals.
- Posted entries are not deleted; corrections use reversal/adjustment with audit history.
- Preserve original bank remarks and debit/credit classifications; duplicates are candidates, not automatically discarded; ambiguous entity matching requires review.
- Approved weekly reconciliation values are historical snapshots; later transactions must not rewrite them.
